# AI Business OS Standard

# 03_NAMING

Version: 1.0

---

# Purpose

Naming is architecture.

A good name communicates purpose before explanation.

Names should reduce ambiguity, improve readability, and remain meaningful as the operating system grows.

Every name should make the system easier to understand.

---

# Philosophy

A name is not a label.

A name is a decision.

Choose names that describe intent rather than implementation.

Prefer timeless concepts over temporary technology.

---

# General Principles

## Be Clear

Names should be immediately understandable.

Prefer:

- Knowledge
- Projects
- Reviews

Avoid:

- Stuff
- Data
- Misc
- Temp

---

## Be Consistent

The same concept should always use the same name.

Never create synonyms for the same idea.

Example:

Always use:

Knowledge

Never alternate between:

Knowledge

Information

Memory

Database

Repository

---

## Be Short

Short names are easier to remember.

Prefer:

Projects

Avoid:

ProjectManagementResources

---

## Be Timeless

Technology changes.

Names should not.

Avoid technology-specific terms unless absolutely necessary.

---

# File Naming

Use:

- UPPERCASE for numbered core documents.
- lowercase for knowledge documents.

Examples

```text
00_INFORMATION_ARCHITECTURE.md

01_MANIFESTO.md

02_FOUNDATION.md

03_ARCHITECTURE.md

04_CONSTITUTION.md

05_BRAND_IDENTITY.md
```

Knowledge

```text
company.md

brands.md

projects.md

people.md
```

---

# Folder Naming

Folder names are always:

- lowercase
- singular when representing a concept
- plural when representing collections

Examples

```text
knowledge/

playbooks/

standards/

ai-workers/

docs/
```

---

# Layer Naming

The architecture uses fixed layer names.

- Foundation
- Identity
- Knowledge
- Execution
- Review
- Evolution

Never rename these layers.

---

# AI Worker Naming

AI Workers describe responsibilities.

Not personalities.

Good examples

- Executive AI
- Creative AI
- Knowledge AI
- Sales AI
- Operations AI

Avoid:

- Super AI
- Genius AI
- Smart AI

Responsibilities should always be obvious.

---

# Document Naming

Each document answers one primary question.

Document names should describe that purpose.

Good examples

- FOUNDATION
- MANIFESTO
- CONSTITUTION
- ARCHITECTURE

Avoid vague names such as

- Notes
- Ideas
- Draft2
- Final_Final_v3

---

# Version Naming

Semantic Versioning is recommended.

Examples

```text
v1.0

v1.1

v2.0
```

Never use

```text
final

new

latest

copy
```

---

# Naming Rules

Every name should satisfy these questions.

- Is it clear?
- Is it consistent?
- Is it scalable?
- Will it still make sense five years from now?

If the answer is "No", rename it.

---

# Review Checklist

Before creating a new file or folder, verify:

- [ ] The purpose is obvious.
- [ ] The name matches existing conventions.
- [ ] The name is future-proof.
- [ ] The name avoids unnecessary abbreviations.
- [ ] The name is understandable without explanation.

---

# Closing

Clear names create clear systems.

Clear systems create better decisions.
